以下の表は、スキャナーの仕様、模擬ラボを使った単体テスト、アプリのソースに基づく期待値です。この文書は実機での実行結果を記録していません。実際の結果は、その実行で保持された CI の証拠と、手元のスキャンで確認してください。

## 期待されるマトリクス(W2、W3、W6)

| `/admin` を要求するアクター | VULNERABLE | HARDENED |
| --- | --- | --- |
| 未認証 | `/login` へ 303 | `/login` へ 303 |
| `alice`(ロール `user`) | 200、管理画面が表示される | 403 |
| `admin`(ロール `admin`) | 200、管理画面が表示される | 200、管理画面が表示される |
| ログアウト後の `alice` の古いトークン | `/api/profile` は 401、`/admin` は `/login` へ 303 | 同じ |

スキャナーの判定はモードではなく、セキュリティ上の条件で決まります。一般ユーザーや未認証の要求が管理画面に到達すれば FAIL(`USER_ADMIN_ACCESS`、`ANON_ADMIN_ACCESS`)です。ログアウト後のトークンがなお認証されれば FAIL(`SESSION_RETAINED`)です。表にない応答は PASS ではなく ERROR です。VULNERABLE モードでは LAB-01 が `USER_ADMIN_ACCESS` の FAIL、HARDENED モードでは PASS になる想定です。

## 原因と修正(W4、W5)

認証は「この人は誰か」、認可は「この人にそれを許してよいか」を決めます。VULNERABLE モードでは、`app/main.py` の `/admin` ハンドラーがログイン中のユーザーを取得しますが、ロールを比較しません。そのため、認証済みであれば誰でも通ります。

正解は B です。サーバー側で、リクエストごとに判断し、既定で拒否します。既存の HARDENED のガードが最小の形です。

```python
if user.get("role") != "admin":
    raise HTTPException(status_code=403, detail="Access denied: Administrator role required.")
```

これは「誰かログインしているか」の確認の後ろに置きます。未認証の要求は引き続き `/login` へリダイレクトされます。A(リンクを隠す)、C(ブラウザの JavaScript)、D(ネットワークアドレス)は、URL に到達できる状態を残すか、要求側が制御できるものに判断を預けるため、方針を強制できません。ガードは `admin` 以外のロールを拒否するだけなので、管理者の利用は引き続き動きます。

## 古いトークンの確認(W6)

`GET /logout` は両モードで、Cookie を消し、サーバー側のセッション記録も削除します(`app/auth.py` の `clear_session_cookie` が `app/db.py` の `delete_session_record` を呼びます)。再利用されたトークンはどのセッションにも一致しないため、`/api/profile` は 401、`/admin` は `/login` へのリダイレクトになります。スキャナーは、本人確認が取れたトークンだけをログアウトし、別のクライアントで再利用します。

## 限界(W7)

- このチェックは、1つのルートに対する3つのロールと、ログアウト後のトークン再利用だけを扱います。他のルートや、オブジェクト単位の所有権は扱いません。
- 検出0件や6件の PASS は、この演習のローカルチェックでは何も見つからなかった、という意味にとどまります。本番での安全性ではありません。HARDENED モードも教育用です。固定の平文パスワード、`Secure=False` の Cookie、期限のないセッション、GET によるログアウト、認証なしの `/audit-logs` が残っています。
- スキャナーは HTTP クライアントでありブラウザではありません。GET によるログアウトには、それ自体の CSRF 上の制約があります。
- 古いトークンの確認は `alice` のトークンが対象です。管理者トークンの再利用は検証していません。
- この演習の完了は、独力でコードを書ける力を示しません。教育効果も主張しません。

## 応用: `/reports/{id}`(W8)

期待される確認は次のとおりです。認証を要求する。レポートを読み込む。返す前に、所有者と要求者を比較する(または明示的な共有ルールに照らす)。既定で拒否し、他人の id が存在するかどうかを応答から推測できないようにする。同じルールをこのルートの全メソッドに適用する。テストマトリクスは、未認証、所有者、別のユーザー、管理者(管理者が全レポートを読める設計の場合)、存在しない id、ログアウト後のトークンです。残る限界は、このテストが、自分で選んだ id とロールしか確かめられないことです。

## ルーブリックの例

自己採点(各軸 0、1、2)の目安です。閾値ではありません。

- R-POLICY: 2 は、`/admin` に到達できるのは `admin` だけで、未認証はログインへ誘導され、管理者は引き続き成功する、と述べています。
- R-MECHANISM: 2 は、`/admin` ハンドラーに欠けていたサーバー側のロール判断を挙げ、A・C・D を理由付きで退けています。
- R-VERIFICATION: 2 は、HARDENED の結果について、許可された管理者とログアウト後のトークンを含む、W2 の4アクターすべてのステータスを引用しています。
- R-LIMITATIONS: 2 は、具体的な限界(例: オブジェクト単位の権限)を挙げ、方針を `/reports/{id}` に適用しています。
